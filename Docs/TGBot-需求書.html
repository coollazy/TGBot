TGBot 需求書

給 Swift 開發者使用的 Telegram Bot Library

版本：v1.4 日期：2026-08-14 狀態：需求已確認（含三輪審查後補強）
本文件是需求確認書，目的是確認「開發者會需要 TGBot 具備哪些能力、解決哪些問題」。 刻意不包含任何實作方式、模組分層、程式碼範例等架構設計內容 ── 那些屬於下一階段的架構設計文件，會在本文件確認後另外產出。

1. 文件目的與範圍

確認 TGBot 這個 Swift Library 要解決開發者的哪些問題、提供哪些能力，作為後續架構設計的依據。本文件不涉及技術選型或實作方案。

2. 專案概述

名稱：TGBot

定位：一套 Swift Package，讓工程師能開發 Telegram 機器人，核心價值在於簡化「連續對話」與「選單互動」這兩件事，讓開發者不需要自己從零設計對話狀態管理機制。

目標使用者：使用 Swift 開發 Telegram Bot 的工程師，可能是個人專案、也可能是要部署在伺服器上長期運行的正式服務。

3. 開發者需求情境

以下情境來自實際開發 Telegram 機器人時常遇到的需求，用來界定 TGBot 需要支援到什麼程度。

US-1 多任務起點與流程內分支

身為開發者，我希望機器人一開始可以提供多種不同任務讓使用者選擇，且單一任務流程進行中，我可以依照使用者輸入或其他條件，讓對話走向不同的分支，而不被限制只能走固定的單一路線。

US-2 錯誤發生時回退狀態

身為開發者，我希望當流程中某個步驟發生錯誤（例如使用者輸入驗證失敗、呼叫外部服務失敗）時，可以讓對話退回到先前的某個步驟重試，而不是讓整個對話直接中斷或強迫使用者從頭開始。

US-3 長任務執行中仍可回應

身為開發者，我希望機器人在執行耗時任務（例如處理訂單、產生報表）期間，仍然可以回應使用者傳來的其他訊息，並且能讓使用者查詢「目前正在處理什麼、進度如何」，而不是整個機器人卡住無法互動。

US-4 限制可對話的使用者

身為開發者，我希望能選擇性地指定一份允許互動的名單（依 Telegram user ID 或 chat ID）。沒有設定名單時機器人維持公開，任何人都能使用；一旦設定了名單，機器人即自動轉為私人模式，只有名單內的使用者／對話能互動，名單外的訊息會收到明確的拒絕回覆，而非靜默忽略。

US-5 取消／重新開始目前的對話

身為開發者，我希望使用者在多步驟對話進行到一半時，能夠主動放棄目前的流程、讓機器人回到沒有進行中任務的狀態，而不是卡在某一步、或必須關掉機器人才能脫身。取消動作只清空「對話流程」本身，不影響已經在背景執行中的任務（US-3／US-6）——背景任務與主要流程本來就是彼此獨立的，取消後背景任務仍會照原本的方式完成並通知。

US-6 背景任務完成時主動通知

身為開發者，我希望背景任務（US-3）執行完成或失敗的當下，機器人能夠主動傳訊息告知使用者結果（成功／失敗），甚至可以接續詢問下一步，而不是要求使用者自己去查詢才知道任務結果。若使用者同時有多個背景任務在跑，通知內容需要讓開發者能夠識別是哪一個任務的結果（例如通知時能取得該任務的識別碼），實際要不要在訊息裡呈現、呈現成什麼樣子由開發者決定。

4. 功能需求

  • 能夠收發 Telegram 訊息，並處理使用者傳來的各類更新（文字訊息、按鈕點擊等）。
  • 能夠定義「多步驟連續對話」，開發者不需自行管理「使用者目前在對話的哪一步」。
  • 連續對話中，能依條件做分支（對應 US-1）。
  • 連續對話中，能在錯誤發生時退回先前步驟重試（對應 US-2）。
  • 能夠在訊息中提供選單／按鈕，並且使用者的選擇能直接接續到對話流程中，不需要開發者手動比對是哪個按鈕被按下。
  • 能夠執行長時間任務，且該任務執行期間，機器人仍可回應其他訊息與查詢（對應 US-3）。
  • 長時間任務結束（成功／失敗）時，能夠主動傳訊息通知使用者，不需要使用者自己查詢（對應 US-6）。
  • 能夠選擇性地依 Telegram user ID 或 chat ID 設定允許互動的白名單；未設定時機器人公開，設定後自動轉為私人模式，名單外的請求會收到明確拒絕回覆（對應 US-4）。
  • 能夠讓使用者主動取消／中止目前進行中的對話流程（對應 US-5）。
  • 能夠讓開發者提供 Bot Token 給 TGBot 使用，且不強迫特定的取得方式（可直接提供、也可由環境變數提供）。
  • 不同使用者（不同對話）之間彼此獨立，互不影響、可同時進行。
  • 同一個使用者對話中，同一時間僅進行一個主要流程（背景任務不計入此限制，可與主要流程並行），但允許被其他任務（如查詢、說明指令）暫時打斷後再恢復原本進度。

5. 非功能需求

  • 易用性：API 設計需讓開發者容易上手、程式碼容易維護，不需要開發者自行實作狀態機或事件分派邏輯。
  • 對話狀態保存：v1 不要求對話進度跨重啟保留，服務／App 重新啟動後使用者對話進度遺失是可接受的；閒置中的對話 v1 也不要求自動過期清除。
  • 可靠性：單一使用者的錯誤或異常不應影響其他使用者的對話；呼叫 Telegram API 失敗（含斷線、逾時、429 rate limit 等各種失敗型態）時需有明確、可預期的處理方式，不能讓整個機器人卡死或無聲失敗。
  • 可觀察性：開發者需要能夠知道機器人內部發生了什麼事——不只是錯誤，一般操作（收發訊息、狀態轉換、白名單攔截等）也需要能夠被記錄，詳細程度由開發者自行調整。
  • 可測試性：開發者需要能夠在不連接真實 Telegram 服務的情況下，為自己撰寫的對話流程撰寫自動化測試。
  • 部署環境：需能在 macOS 與 Linux 上執行，並支援兩種常見的封裝與交付方式──打包成 Docker image（部署於 Linux server），或打包成 macOS application（供使用者在自己電腦上執行）；最低支援 Swift 6.0（依架構設計階段的實測結果訂定，見架構設計文件）。
  • 使用規模：預期為少量使用者，非高併發、高流量場景，效能與延遲不是主要考量重點。
  • 版本相容性：1.0 版之後，版本更新需遵循語意化版本（SemVer）承諾，次版本／修訂版本更新不應讓既有開發者的程式碼編譯失敗。
  • 文件需求：v1 發布時至少需具備最小上手範例（quickstart）與核心公開 API 的說明文件。

6. 範圍外（v1 暫不處理）

  • Telegram Bot API 的進階功能（如 Payments、Games、Inline Mode）非首版重點。
  • 不提供圖形化管理後台或視覺化流程編輯工具。
  • 不特別針對群組（group/channel）管理場景做最佳化，優先聚焦一對一對話。
